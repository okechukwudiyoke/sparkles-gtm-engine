# Ghost prospect research packet

**Research date:** 24 September 2026  
**Motion:** delegation + workflow acceleration  
**Purpose:** Second worked account for the Sparkles GTM demo. This is not a claim that Ghost is a Sparkles customer or that the hypotheses below are true.

## Why Ghost is useful as a contrasting account

Ghost is a more conventional product/publishing organisation than Sentry for this exercise. Its public materials show:

- a substantial open-source product and official docs codebase;
- engineering/development alongside product, design, brand, support and infrastructure roles;
- GitHub pull-request previews for documentation;
- merge-to-main deployment;
- explicit pre-PR testing and validation.

That creates a different Sparkles GTM question:

> Can cross-functional teammates ship bounded changes themselves while keeping the organisation's existing preview, testing, review and merge controls intact?

## Public evidence

### g1 — cross-functional organisation + existing product
Source: https://ghost.org/about/

### g4 — business / marketing surface

### g5 — sustainable hosted business
Source: https://ghost.org/about/

Ghost publishes business metrics and describes a paid managed service funding the open-source product.

## What we can infer safely

- Existing production codebase: **yes**
- GitHub PR / review workflow: **yes**
- Automated validation before merge: **yes**
- Cross-functional non-engineering roles: **yes**
- Current AI-coding-tool usage: **unknown**
- Non-engineering request backlog: **unknown**
- Buyer / budget: **unknown**

## GTM hypothesis

The likely wedge is not "use AI because AI is new." It is:

**bounded request → agent-assisted implementation → preview/tests → reviewable PR → existing approval**

For Ghost, the proof should emphasize reduced engineering interruption, shorter iteration cycles and retention of the current delivery controls.
